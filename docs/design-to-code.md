# 디자인 구현 프로세스

디자인 링크를 기반으로 UI를 구현할 때 적용한다.

## 기존 자산 확인

- 디자인의 색상, 타이포그래피, 간격, radius, border, shadow를 `src/shared/styles`의 토큰과 비교한다.
- `src/shared`의 공통 컴포넌트와 variant, state, 접근성, 반응형 동작을 확인한다.
- 토큰 이름뿐 아니라 유사 화면에서 같은 역할의 UI에 실제로 사용한 토큰과 컴포넌트를 확인한다.

## 재사용 및 추가 기준

- 디자인과 기존 토큰이 일치한다고 가정하지 않는다. 새 값이나 컴포넌트를 추가하기 전에 기존 사용 방식을 확인한다.
- 시각적 차이가 작고 의미, 사용성, 접근성, 레이아웃에 무리가 없다면 기존 항목을 재사용해 코드의 일관성을 유지한다.
- 대체로 인해 의미나 상태가 달라지거나 시각적 차이가 크면 새 토큰 또는 컴포넌트의 추가·확장을 제안한다.
- 합의되지 않은 임의의 raw color나 반복되는 magic number를 추가하지 않는다.

## 구현 전 공유

차이가 있으면 해당하는 항목만 다음 기준으로 간결하게 공유한다.

| 구분 | 공유할 내용 |
| --- | --- |
| 기존 항목으로 대체 | 원본 → 적용 값·컴포넌트, 기존 사용 위치, 변경 이유와 시각적·사용성 영향 |
| 새 토큰 | 이름, 값, 의미, 기존 토큰으로 대체할 수 없는 이유, 사용처 |
| 컴포넌트 추가·확장 | 이름과 책임, 추가·확장 여부, variant·state, 재사용 위치, 접근성·반응형 기준 |

사용자가 즉시 구현을 요청한 경우에는 제안 사항을 공유한 뒤 계속 작업한다. 사용자의 선택이 결과를 크게 바꾸는 경우에는 구현 전에 방향을 확인한다.

## 구현 및 결과 보고

- 공유한 방향에 따라 토큰과 컴포넌트를 사용·추가한다.
- 디자인과 프로젝트 규칙이 충돌하면 프로젝트 규칙에 맞게 조정하고 그 차이를 알린다.
- Figma와 다르게 구현한 부분은 대상별로 원본 → 적용 내용, 이유, 영향을 간결하게 정리한다.
- 차이가 없으면 `Figma와 다르게 적용된 항목 없음`이라고 명시한다.
